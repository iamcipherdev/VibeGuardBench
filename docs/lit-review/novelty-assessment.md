# Novelty Assessment and Gap Definition

**Status:** Frozen with protocol v1.0.0. Written *before* any experimental data collection.

## 1. The novelty challenge, stated honestly

The proposed study does **not** claim "first" status in any of its component parts:

- Testing AI-generated patches with regression awareness exists (SWE-bench family).
- Measuring patch overfitting and regression breakage in automated program repair
  exists (Smith et al. 2015; Poracle 2023; Lou et al. 2024; Petke et al. 2024).
- Iterative degradation of LLM editing exists (CanItEdit; Self-Refine; LLMs-cannot-
  self-correct).
- Security measurement of AI-generated code exists (Perry et al. 2023; Pearce et al.
  2022, 2023).
- Automated functional evaluation of LLM-generated websites exists (WebGen-Bench).

## 2. What the search did and did not find

The search (16 queries, 2026-09-14, see `search-log.md`) found **no empirical study
that combines all of the following**:

1. Applications generated by commercial, prompt-driven AI app builders (the systems
   marketed for "vibe coding" of full-stack products), with source code exported.
2. A deterministic, multi-category QA oracle suite over the *exported* application:
   build/install, type checking and linting, browser-level functional behavior,
   authorization behavior, static security scanning, secret detection, accessibility
   (axe-core), and database persistence.
3. A repair protocol in which the *same builder* receives machine-generated, fixed-
   template feedback describing failures, with **the entire oracle suite re-executed
   after every repair**, at every iteration.
4. Quantification of the repair-regression trade-off across iterations: how many
   targeted failures are fixed, how many previously passing checks break, and how that
   trajectory evolves.

The closest adjacent work and why it does not cover the combination:

- **WebGen-Bench** (NeurIPS 2025) evaluates initial generation of websites with
  automated tests. It does not study repair loops, security, accessibility, or
  regression introduction.
- **SWE-bench / SWE-agent / Agentless / AutoCodeRover** evaluate issue-resolution
  patches on human-authored Python repositories with unit tests. The artifact is a
  repository issue, not a generated full-stack app; oracles are unit tests, not
  browser-level functional, authorization, accessibility, or persistence checks; the
  repair driver is an engineering agent, not the original commercial builder receiving
  deterministic feedback.
- **CanItEdit** studies successive instructional edits at function level with tests;
  it does not involve app-level artifacts or non-functional oracles.
- **Lou et al. (TOSEM 2024)** measures regression failure of APR patches at scale, but
  for classical APR tools on Java/C — not LLM repair, not app-level, not NFR oracles.
- **AppWorld** verifies agent programs against simulated apps, not the internal quality
  of generated application codebases.
- **The Vibe Coding survey (Ge et al., arXiv 2510.12399)** explicitly frames
  reliability and security of vibe-coded products as open empirical problems.

Commercial comparison content (Lovable vs Bolt vs v0 articles) exists in quantity but
is vendor/blog material without reproducible methodology, without deterministic
oracles, and without regression accounting.

## 3. Resulting gap statement (for the manuscript)

> Our search found limited empirical evidence specifically examining whether
> prompt-driven AI app builders can repair deterministic, tool-detected failures in
> their own generated full-stack applications without breaking previously passing
> checks. Prior work evaluates initial quality of generated web applications, repair
> of human repositories against unit tests, and patch overfitting in classical APR,
> but fewer studies explicitly quantify repair gains together with newly introduced
> regressions under deterministic QA feedback at the whole-application level, with
> security and accessibility oracles included.

This wording avoids a "first study" claim and survives the adjacent literature above.

## 4. Refined research questions

Changes from the initial draft, with rationale:

- **RQ1 (repair effectiveness)** retained: proportion of objectively detected failures
  that become passing after deterministic feedback, per repair iteration.
- **RQ2 (regression introduction)** retained and sharpened: regressions are defined
  only against the *pre-repair* full-suite execution (never against a failing
  baseline), and are measured per category.
- **RQ3 (category differences)** retained, with categories fixed a priori:
  functionality, authentication/authorization, security, accessibility, build
  reliability, database persistence, type correctness, maintainability (lint).
- **RQ4 (trajectory across iterations)** retained: shape of the repair-regression
  trajectory over up to 3 repair iterations; includes testing whether gains diminish
  or reverse.
- **RQ5 (builder differences)** demoted from a primary RQ to an **exploratory,
  conditional comparison**. With 2 builders × 3 tasks × 3 repetitions (18 apps), the
  design supports estimation with wide uncertainty per builder, not a powered
  confirmatory comparison. RQ5 is only reported descriptively with interval estimates,
  and the manuscript will say so.

One question was **removed** during refinement: an earlier draft asked whether repair
success differs "across AI builders" as RQ2 and regression as RQ3. The refined
numbering keeps regression (RQ2) before category differences (RQ3) because RQ2's
denominator logic depends on RQ1's targeting rules; the dependency must be presented
in order.

## 5. Novelty survival check

If, before data collection, a new publication is found that measures repair-versus-
regression behavior of commercial AI app builders under deterministic multi-category
QA feedback, this project will be re-scoped (e.g., to builder-comparison, NFR-focused,
or replication-with-variation work) and this file updated with the overlap analysis.
