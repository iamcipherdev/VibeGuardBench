## SUMMARY

This is a preregistration-style research protocol (no results claimed) measuring whether commercial AI app builders can repair deterministic QA failures in their own generated full-stack applications without breaking passing checks. The study design is genuinely well conceived: frozen specifications with binding interface contracts, a whole-suite re-execution rule, machine-generated fixed-template feedback, transition-level metrics (RSR/RR/NQC) with a pre-declared cluster-bootstrap analysis plan, honest scope limitations, and a demoted exploratory builder comparison. However, the *implementation* — which the paper explicitly equates with the protocol ("The repository accompanying this document is the protocol") — deviates from the protocol's frozen claims in several measurement-critical ways. I verified one empirically: the frozen ESLint config has no environment globals, and the pilot's persistent "16 lint errors" — which the pilot README and the manuscript attribute to plausible model behavior — are 100% `no-undef` hits on `require`/`process`, i.e., a harness artifact, not an application defect. I further identified an interaction between Playwright `describe.serial` skipping and the implemented metric code (`analysis/metrics.py` lines 49–50) that systematically drops outcome-dependent check outcomes from RSR/RR denominators, undercounting exactly the regressions RQ2 is designed to measure (e.g., a repair that breaks login masks ~13 subsequently-skipped checks). Additional verified issues: run-record timestamps are fabricated (start = finish = write time), `dep_manifest_diff` is always null despite being a protocol-mandated confound mitigation, the shipped run records cannot validate against the shipped schema, the SEC-005 token-variant verdict is discarded by a first-wins dedup, the engine's server-stop lacks the process-group fix (risking false DB-pass results measured against orphaned processes), the protocol's retry policy is unimplemented, and the protocol/paper/catalog disagree on the scale of the study (45–60 vs. 39–45 applicable checks per app against a 39-check catalog; 3,000–4,000 vs. 2,800–3,000 observations). The statistical plan is sound at the design level but entirely unimplemented and untested, which sits awkwardly with the paper's freeze logic. Because the central contribution is measurement validity and the harness demonstrably contradicts the frozen protocol on several measurement-critical points, the work is not yet acceptable as-is; the defects are concrete and fixable before data collection.

## STRENGTHS

1. **Genuine preregistration posture.** Specifications, prompts, check catalog, metric definitions, exclusion rules, and the analysis plan are frozen with a changelog discipline that records rationale and phase (pre-data). Amendments from pilot findings are documented (v1.0.1) and the pilot is explicitly excluded from research claims.
2. **The whole-suite rule is correctly motivated and implemented as stated** — every category re-runs after every repair; `run_oracles.py` executes all categories on every invocation, and no "run only failing checks" shortcut exists in the code.
3. **Deterministic-feedback design removes the LLM-judge confound.** Feedback is rendered by `make_feedback.py` from frozen per-check templates; the operator is forbidden to rephrase; env-error checks are excluded from the feedback body per the frozen template doc.
4. **Metric definitions at the protocol level are reasonable**: transition-defined RSR/RR, raw counts alongside rates, small-denominator flags, a pre-registered dependency caveat with a cascade-exclusion sensitivity analysis, and environment-error/n-a exclusion semantics.
5. **Honest scope discipline.** RQ5 is demoted to exploratory with an explicit non-power statement; external/conclusion validity threats are stated rather than argued away; the gap claim is a "coverage gap," not a "first," supported by a verified related-work matrix with machine-readable citation records.
6. **The pilot did catch real harness defects** (prompt truncation, output protocol, health-check redirect semantics, Semgrep config error, missing logout tests, cross-iteration state pollution), and the changelog amendments for them are sensible and pre-data.
7. **Security interpretation rules (§6.4)** — candidate-finding status, manual verification, sensitivity analysis, no CVSS/severity language — are methodologically correct, and the fairness framing of the prescriptive-contract trade-off is candidly recorded in both protocol and paper.

## MAJOR CONCERNS

### 1. The frozen LINT oracle is broken, and the pilot + manuscript misattribute its failures to model behavior (empirically verified)

`oracles/build/eslint.config.mjs` enables `no-undef: "error"` (and `sourceType: "module"`) but declares **no `globals` for any environment** (no `globals` key anywhere in the file). I executed this exact frozen config against the pilot application (`pilot/app-r1-i000/server.js`): the result is exactly **16 errors, all `no-undef` — `'require' is not defined` (×5), `'process' is not defined` (×2), plus further `require`/`process`/module-global hits** — precisely the "16 errors" reported at all three pilot iterations. Every Node app using CommonJS (and every app with browser-side JS using `window`/`document`/`fetch`) will fail LINT-001 regardless of code quality; browser apps will additionally fail on DOM globals.

Consequences: (a) the pilot README's claim that persistent failures "are *the model's* repair dynamics, not harness errors" is wrong for LINT-001 — a harness defect was misclassified as model behavior, the exact failure mode the pilot existed to eliminate; (b) the manuscript (sec-body1, "Status of Results") repeats this misattribution ("Persistent failures—… lint errors …—are plausible model behavior"); (c) in the study, the LINT category of RQ3 would measure whether builders refactor CommonJS→ESM or add `/*global*/` comments, not maintainability; (d) the LINT feedback ("Fix the reported rule violations: 16 errors") does not even include the rule IDs or messages (the run record's `detail` is empty), so builders cannot diagnose the failures — LINT RSR would be noise. This must be fixed pre-data (add `globals` for node/browser or use `languageOptions.globals` per file class), and the changelog must record the amendment; the manuscript's pilot narrative must be corrected.

### 2. Outcome-dependent `na` (soft cascade) plus the implemented metric denominators systematically undercount regressions — the core construct of RQ2

Two interacting problems, both verified in code and in the pilot data:

- **Soft cascade via `describe.serial`.** All three functional specs wrap all FUNC/A11Y/AUTHZ-004 tests in `test.describe.serial` (e.g., `app01.spec.js` line 8). In Playwright serial mode, the first failure **skips all subsequent tests in the group**; `run_oracles.py::walk_suites` maps `skipped` → `na`. In the pilot i000 record, a single FUNC-001 failure (login selector timeout) turned **17 checks** (FUNC-002..011, AUTHZ-004, A11Y-001..004) into `na` even though the app server was running and engine-based AUTHZ/DB probes executed normally. The protocol defines only one cascade (build-start failure → runtime n/a); this outcome-dependent, prerequisite-driven `na` is undocumented, unamended, and uncontrolled.
- **Denominator filtering in the metric implementation.** `analysis/metrics.py` lines 49–50 restrict both RSR and RR denominators to checks whose k+1 outcome is `pass` or `fail` — i.e., checks that become `na`/`env-error` at k+1 (or vanish) are dropped from the denominators. The protocol's frozen formula defines the denominator as |T(a,k)| and |P(a,k)| *at iteration k*. The implemented variant makes the denominator a function of the k+1 outcome.

Joint effect: a repair that breaks login (or the build) causes the masked checks to become `na` at k+1 and therefore to **disappear from both the RSR and the RR denominators**. Example with pilot-like numbers: at iteration k, 14 checks pass and login works; the repair breaks login at k+1 → FUNC-001 counts as one regression, while the other ~13 previously passing checks are skipped to `na` and excluded — RR is reported as ~1/14 instead of ~14/14; symmetric effects select RSR's denominator toward whichever targets remained measurable. A repair that fails the build entirely can produce RR ≈ (a few BUILD checks)/N with all runtime damage invisible. This is a structural undercount of regressions — the study's headline construct — and it also biases cross-category comparisons (FUNC/A11Y categories are precisely the ones subject to the serial skip). Additionally, root-cause handling is inconsistent: a persistence-role login failure yields `env-error` for DB-001 (excluded from metrics; engine.mjs line 276) but the identical root cause yields `fail` for AUTHZ-002/003/005/006 ("login failed"; engine.mjs lines 185–224), contaminating the AUTHZ category with non-authorization failures.

Required: distinguish "n/a by design" (contract, stack) from "masked by prerequisite" in the outcome vocabulary (or record `masked_by`), freeze a correction in the changelog pre-data, and re-implement the metrics so denominators are fixed at iteration k per the frozen formulas (with masked outcomes either imputed as not-passed or reported separately — chosen and documented *before* data collection).

### 3. Protocol, paper, and catalog disagree on the scale of the study — and the protocol's number is impossible

- Protocol §2: "The frozen check catalog contains approximately **45–60 applicable checks per application** … roughly **3,000–4,000** check observations."
- Paper (sec-body1): "roughly **39–45** applicable checks per application … roughly **2,800 to 3,000** eligible observations."
- Frozen catalog: **39 checks total**. 45–60 applicable is arithmetically impossible; even 39–45 is impossible (max applicable ≤ 39).
- Actual eligibility is lower still: the pilot's fully-executed suite shows **20 eligible checks** (14 pass + 6 fail) with 19 `na` (BUILD-002 no build script; TYPE-001 non-TS; FUNC-005 contract-n/a; DB-002 no update probe; SEC-005 token-variant; plus the 17-check serial skip). Applicability is endogenous to stack choices (TYPE-001 only for TypeScript; BUILD-002 only when a build script is declared), so the *typical* eligible count per app-iteration is plausibly in the low-to-mid 20s–30s, not 39–45.

The "justification of scale" in §2 — the only sample-size reasoning in the protocol — is thus built on numbers that cannot occur, and the two documents do not even agree with each other. This matters for the design's central defense against the small-N objection (3 repetitions): the realized observation count, and therefore the precision narrative, is materially smaller than advertised. Reconcile all three documents pre-data with honest eligible-count estimates (per task, per plausible stack), and re-state the scale justification.

### 4. Primary metrics are structurally blind to whole classes of quality change (construct validity of RSR/RR/NQC)

By frozen definition, NQC = |repaired| − |regressed| counts only fail→pass and pass→fail transitions. Transitions **na→fail, fail→na, pass→na** contribute zero. The pilot itself demonstrates the problem: at i1 the repair caused SEC-005 to flip na→fail (the app switched from a body token to an unflagged cookie) — the app strictly worsened, yet the manuscript reports "repaired 0 of 6 … regressed 0 of 14" and NQC = 0, without mentioning the newly induced failure. Similarly, fail→na (build breakage) reduces the recorded failure count without any repair. Trajectory claims (RQ4: "diminishing returns, reversal, oscillation") are computed on these metrics and additionally suffer from selection: apps that reach zero failures stop early (their later "stability" is unobserved), and prerequisite-masked categories only re-enter the measurable set when a prerequisite is repaired, so iteration-index effects are entangled with changing eligibility. The paper should either (a) extend NQC with na→fail and fail→na flows as co-primary descriptive quantities, or (b) explicitly bound the interpretation of NQC/trajectories, pre-data, in the changelog. Reporting the pilot as evidence the machinery "measures such dynamics" while the machinery's own summary concealed a new failure argues for (a).

### 5. Provenance fields in the run records are not real measurements; "schema-validated" is false as implemented

Verified in `run_oracles.py::finalize` (lines 495–509): `started_utc` and `finished_utc` are both `NOW()` evaluated at record-write time — every pilot run record has identical start/finish instants (e.g., i000 `01:50:19Z`/`01:50:19Z`; i001 `01:54:02Z`/`01:54:02Z`), so execution duration and ordering provenance required by protocol §7 do not exist. `dep_manifest_diff` is hard-coded `null` — yet the dependency-diff log is the protocol's stated mitigation for the "different dependency versions across iterations" confound (§11). `builder_platform` fields (tier, model disclosure, platform version, generation mode, settings) are hard-coded nulls/"unknown" — the protocol §4 requires them per run, and they can only be satisfied by hand-editing machine-written records, which conflicts with the provenance model. The shipped run records **cannot validate against the shipped `run-record.schema.json`** (it requires `env.os`, `env.tsc`, `env.eslint`, `env.axe_core`, absent from `env_report()`'s output), and no code path validates anything (`ledger.py`'s docstring says "validates structure" but performs no validation). `Checks.add` accepts a `raw_key` argument and silently discards it; raw tool output for install/build/tsc/eslint/semgrep/audit is not archived anywhere (only ≤500-char snippets), contrary to §7's "machine + raw tool output." Individually small, collectively these mean the audit trail the protocol promises — the thing that makes the single-operator design checkable — is not what the code produces. Fix pre-data: real start/stop timestamps, computed dependency diffs, populated platform fields, a schema validator that runs and fails loudly, and per-check raw-output archival.

### 6. DB persistence probes can be measured against an orphaned stale process (false passes), and the claimed fix exists in only one of two server launchers

`engine.mjs` spawns the app server with `spawn(cmd, { shell: "/bin/bash", … })` and **no `detached: true`**; `stop()` sends SIGTERM/SIGKILL to the shell PID only (lines 119–136). With `npm start` the node child is not in the killed process and frequently survives. The pilot's claimed fix ("Now uses process groups") was applied only in `run_oracles.py` (`start_new_session=True` + `os.killpg`), not in `engine.mjs`, which launches its own server instances for AUTHZ/DB probes and restarts the server 1–3 times inside `dbProbes`. Failure mode: after `server.stop()`, the orphaned node process keeps the port bound; `waitForServer()` succeeds because the **orphan** answers; DB-001/002/003 are then evaluated against the old process. For an in-memory-storage app — precisely the defect DB-001 exists to detect — the orphan retains state and the persistence check **falsely passes**. This is a plausible, unmitigated threat to one of the eight categories. Fix pre-data: process-group kill (or `detached: true` + `process.kill(-pid)`), plus a post-stop assertion that the port is actually free before restart, and log it.

### 7. The frozen protocol's retry policy is unimplemented, while the feedback text asserts the opposite

Protocol §6.3: environment-class failures are "retried exactly once and the retry is logged." `run_oracles.py` implements no retry of anything (`retries: []` is always empty; Playwright config has `retries: 0` — correct for test-content failures, but there is no runner-level retry for env-class failures either); `walk_suites` even maps Playwright status `flaky` to `fail` without any retry accounting. Meanwhile `make_feedback.py` tells the builder "Environment errors (not your fault, **will be retried**): …" — a promise the harness never keeps. Env-error checks are excluded from all metrics, so an un-retried env-error silently removes checks from an iteration. Either implement the single logged retry or amend §6.3 pre-data and fix the feedback text; do not leave the two inconsistent.

### 8. The statistical analysis plan is frozen but unimplemented and untested — and has unresolved estimand ambiguities

`analysis/` contains only `metrics.py` (pooled counts and per-transition rates) and `plots.py` (trajectory figure). Nothing implements the cluster bootstrap (2,000 replicates), the BH corrections, the mixed-effects model with its pre-declared fallback rule, or the cascade sensitivity analysis. The paper's contribution list claims "a metrics and analysis pipeline." Beyond the missing code, the plan has ambiguities that should be resolved while amendments are still free: (a) the point estimate for pooled RSR/RR under cluster resampling is undefined — ratio-of-sums (pooled counts) and mean-of-per-app-ratios are different estimands with different variance behavior, and `metrics.py` currently computes only pooled counts; (b) percentile bootstrap CIs with 18 clusters are known to under-cover (and will be degenerate for categories where only one or two apps have any failing check — likely for TYPE, and possibly SEC/A11Y); (c) the pre-declared mixed logistic model (`outcome ~ iteration × category`, random intercepts for app and check) estimates marginal pass probability at an iteration, **not** the transition probabilities RSR/RR that RQ3/RQ4 are defined on — using it for those RQs is an estimand mismatch that should be reconciled (e.g., model the transition indicators directly); (d) the design is matched by task across builders, but the plan never exploits the pairing for RQ5's descriptive intervals. Implement and dry-run the full analysis on synthetic data with known truth, pre-data, consistent with the project's own freeze logic.

### 9. Applicability logic lives in code, not in the frozen catalog; spec/contract/oracle inconsistencies produce arbitrary outcomes

The catalog says `applies_to: "all"` for every check, but actual applicability is decided by hardcoded per-task lists in `run_oracles.py` (`FUNC_APPLICABLE`, lines 37–44; FUNC-005 excluded for APP-01, FUNC-006 for APP-02/03), by runtime declarations (BUILD-002 n/a when no build script; TYPE-001 only with tsconfig.json), by contract fields (`persistence_update: null` → DB-002 n/a), and by auth design (SEC-005 n/a for token-based apps). The "frozen catalog" therefore does not determine the measurement; the code does — and code is not covered by the amendment discipline. Concrete inconsistencies: (a) APP-03's contract sets `persistence_update: null` although the spec requires stock-update persistence via `PATCH /api/products/{id}` (§6: "stock updates … survive restart") — DB-002 is unmeasurable for APP-03 but measurable for APP-02, a cross-task asymmetry in the DB category; (b) APP-01 spec §6 D1 says "created, **edited**, and deleted appointments survive restart" while the APP-01 contract has no edit endpoint — the spec contradicts its own contract; (c) the CHANGELOG claims "Check-catalog wording: BUILD-004 template updated (200 or redirect)" but `check-catalog.json` still says `"Root URL reachable (HTTP 200)"` / "expected 200" — the claimed amendment was not applied to the file it names (only `run_oracles.py` line 306–307 implements it); (d) APP-01 §2.2 "201 `{appointment}`" suggests a nested response while §2.3 and `create.schema` validate a flat object — a spec-compliant nested response fails DB-004 and also breaks `cross_owner_setup` id extraction (engine.mjs line 157 reads only the top-level `id`, unlike the DB-create path which has a nested fallback at lines 290–293), cascading into spurious AUTHZ-003/005 failures against compliant apps; (e) AUTHZ-005 is a strict subset of AUTHZ-003's probes (deny-matrix filtered to non-GET), double-counting the same evidence in category denominators. Move applicability into the catalog (or a frozen applicability map), apply the BUILD-004 wording change actually claimed, and resolve (a)–(d) pre-data.

### 10. Weak or style-dependent security oracles, in tension with the spec's own mandates

(a) **SEC-005's token variant is dead code**: `parse_engine` inserts SEC-005 (outcome `na`, "token-based…") *before* `sec006_localstorage` runs and its code-grep verdict is added; `finalize` deduplicates first-wins (lines 481–487), so the localStorage-token verdict is discarded — SEC-005 can never fail for token-based apps, contradicting the paper's description ("cookie flags or non-localStorage tokens"). (b) **SEC-006 passes on mere mention** of bcrypt/argon2/scrypt/pbkdf2 in any `.js/.ts/.json` file — including `package.json` dependencies — with no evidence passwords are actually hashed; the DB scan only searches file-backed SQLite-style DBs, so Postgres/MySQL apps get SEC-006 from dependency presence alone. (c) The spec **mandates** hard-coded seed credentials ("exactly these credentials"), while SEC-001's `hardcoded-password-literal` rule fires on `$V = "…"` assignments to variables named `*password*` — so SEC-001 outcomes depend on whether the builder writes the mandated seed as an assignment (fail) or an object property (pass); the same tension affects SEC-002's generic-secret pattern. The oracles should be made behavior-sensitive pre-data (e.g., SEC-006 verifies a hash of a probe credential actually stored, or is recorded n/a-not-pass; SEC-001 whitelists the frozen seed literals) and the tension documented. (d) Pilot feedback files archive a full live JWT in plaintext (`feedback.txt`, i001 SEC-005 section) — the protocol's own redaction/ethics rules (§14) require secrets to be redacted in public archives; the feedback generator needs an observed-value redaction pass (also for cookies/tokens in AUTHZ/SEC observed fields).

### 11. Pilot data and future study data share one pipeline with no separation mechanism

`ledger.py` globs every `run-record.json` under `data/raw/runs/` and `metrics.py`/`plots.py` consume the result unfiltered. Pilot runs (`APP-01-PILOTGLM-*`) already live in that tree (136 rows in the shipped `check-observations.csv`). Nothing except manual diligence prevents pilot rows from entering study aggregates — the protocol's "excluded from all research claims" is currently enforced by convention only. Provide a builder/task allowlist or separate data roots for pilot vs. study data pre-data, and have the analysis scripts assert it.

### 12. Feedback truncation is category-differential and its documentation is contradicted by the code

The frozen feedback template (rule 3) says truncation at 8,000 characters is "recorded in the run record." `make_feedback.py` records it only in stdout; the run record is untouched. Worse, `pop(-1)` drops sections from the end of a check-ID-sorted list, so under truncation **SEC and LINT failures are dropped first** (alphabetically last) while A11Y/BUILD survive — a systematic, category-differential denial of repair opportunity that directly biases RQ3's category comparisons for exactly the categories most likely to co-occur with many failures (SEC-003 + LINT-001 are common co-failures, as the pilot shows). Also, the truncation note is appended *after* the length check, so the final body can exceed MAX_LEN. Fix pre-data: round-robin or category-stratified truncation, record truncation in the run record, and re-check length after appending the note.

1. `runbook.md` §A.6 gives `python runner/run_oracles.py --run-id {RUN_ID}` but the script requires `--task --builder --rep --iteration --app-dir`; the frozen operator instructions are unexecutable as written. §D references an operator-log template "in this directory" that does not exist in `benchmark/prompts/`.

13. Protocol §8/§12 do not say what happens if feedback cannot be delivered (platform length limits beyond truncation, session expiry mid-loop). §12's exclusion list does not cover it; add a rule pre-data.
14. `walk_suites` keys results by the first whitespace-delimited token of the test title; two tests sharing a check-ID prefix would silently overwrite each other. Fine now; worth an assertion.
15. The state-reset intervention deletes `*.db` files *inside* the application directory, in tension with the runbook's absolute prohibition on modifying `generated-apps/`; it is logged as an environment intervention, but the runbook wording should carve this out explicitly.
